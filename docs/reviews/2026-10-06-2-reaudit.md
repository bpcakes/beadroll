# bp POC: second independent audit

Reviewed 6 October 2026. **The revisions fix the previous executable reproductions, but claim recovery still fails the stated fault model.** Normal traffic converged in every completed stress run. Targeted interruptions can still fork one machine's journal, let a rejected claim displace an accepted owner after full convergence, or make a reader report a claim that never succeeded.

This report distinguishes ordinary command/network races from hand-written corrupt input. It does not treat persistent claims, thread ownership, local owner closes, child renumbering, serialized publishing, or replay without a persisted projection as bugs.

## Findings

### R01 — High: uncertain push outcomes permit rollback, then an own-journal fork

**Trigger:** ordinary claims, transport uncertainty and another local write. Two independently reproduced boundaries share the unsafe assumption that absence or a nonzero client exit proves remote refusal.

1. A real local pre-receive hook stalls A's claim push. BP_NET_TIMEOUT=0.3 returns REMOTE_UNREACHABLE while receive-pack remains alive. A sync fetches the old head, takes back the pending claim, and reports success because the resulting tree equals the fetched tree. A appends a comment. Releasing the hook lets the original push succeed. B sees that accepted claim; A's next sync fails JOURNAL_FORK.
2. A real successful push is followed by an injected nonzero transport result. The claim handler takes back the accepted event. A separate real local comment process runs during retry backoff. The next fetch now conflicts with that comment and fails JOURNAL_FORK. Without the interleaved writer, the immediate-retry control passes.

**Expected:** an uncertain claim retains its journal bytes/identity until its acceptance is confirmed or remote acceptance has been conclusively fenced off. **Actual:** two different tails occupy the same machine journal position. Further sync requires intervention; the error incorrectly suggests a copied machine identity. This is a durable journal fork, not demonstrated destruction of the remote's accepted event.

Reproductions:

- ProtocolReaudit.test_delayed_push_after_timeout_and_absent_fetch_must_not_fork
- ProtocolReaudit.test_nonzero_applied_push_with_interleaved_writer_must_not_fork

The first uses an actual delayed receive-pack with no mocked client/protocol method. The second mocks the successful push's returned status and schedules the competing writer; actual files, refs, pushes and competing CLI process are real.

Locations: [reconcile](bp:1272), [publish](bp:1223), [coordinated](bp:1338). A no-change tree is not a remote conditional-update barrier. Distinguish explicit ref rejection from transport ambiguity, and do not let a later absent fetch alone erase an attempt still capable of succeeding. No small complete patch is claimed for this protocol change.

### R02 — High under corrupt input: a second create replaces an existing immutable issue

**Trigger:** a hand-written create with a fresh event ID, a new key, and an already existing issue UID. No normal create/import command emits this.

**Expected:** reject the malformed create and preserve the original issue. **Actual:** apply_event unconditionally replaces st.issues[uid]; the original title and associated projected state disappear, and the old key remains an alias to the replacement. No integrity entry identifies the overwrite. The raw journal remains available, so this is projection loss rather than erased source bytes.

Reproduction: ReplayReaudit.test_duplicate_create_uid_does_not_destroy_issue. The original key resolves to title “replacement” instead of “survivor”.

Locations: [payload validation](bp:579), [create application](bp:675). The proposed create-identity diff below requires a create's issue UID to equal its event ID. Its one targeted regression passes on a separate scratch candidate; no full candidate-suite claim is made.

### R03 — High: failed cancellation publication revives rejected claims and edits

**Trigger:** a claim fails before acceptance, independent local work follows, and recovery's cancellation publication then fails or loses a fast-forward race.

A fails to publish its claim, then adds a comment. Reconciliation cannot remove that earlier claim from the tail, so it emits a void. It drops the original claim from unconfirmed.json and marks only the void unconfirmed. If the void push fails, the original is already exposed; retry can take back the void and leave the original permanently active.

**Expected:** unaccepted ownership stays hidden, independent work survives, and B's successful online claim remains authoritative. **Actual:** after B legitimately claims and both machines fully sync, both converge to A's originally rejected claim; B's accepted claim is recorded as lost. A failed atomic update can also revive its title and label changes. This is wrong ownership after convergence, not merely a stale read.

Reproductions, all in ProtocolReaudit:

- test_refused_void_publish_must_not_activate_unaccepted_claim
- test_failed_void_publish_retry_must_not_activate_unaccepted_claim
- test_failed_void_push_must_leave_original_claim_unconfirmed
- test_failed_multievent_update_void_retry_must_not_commit_edits

These inject the same REMOTE_UNREACHABLE exception used for transport failures, before acceptance, and use real Git/CLI contention and convergence thereafter. The successful first-cancellation control passes.

Location: [reconcile marker lifetime](bp:1296). The narrow proposed diff keeps the original event unconfirmed alongside its cancellation. All four reproductions plus two recovery controls pass against that scratch candidate. It does not fix R01.

### R04 — High, transient observation: an unlocked reader can confirm a rejected claim

**Trigger:** an actual show overlaps a losing online claim's rollback.

Pause A's show after it loads the journal containing A's unconfirmed attempt, but before it loads unconfirmed.json. B successfully claims. Resume A's real push: Git refuses it; A removes its local attempt and marker, fetches B, and exits ALREADY_CLAIMED. Resume the paused show. It combines the old journal with the new empty marker set and returns A's never-accepted attempt as a confirmed online generation-1 claim. B simultaneously has a distinct accepted generation-1 owner.

**Expected:** a coherent read never promotes a rejected attempt. **Actual:** a false confirmed owner is returned. Subsequent ordinary reads show B; this test does not demonstrate durable divergence by itself.

With BP_ROTATE_BYTES=1, another paused reader enumerates the losing attempt's new segment before rollback unlinks it. It then crashes opening that path with FileNotFoundError and a traceback.

Reproductions:

- StorageReaudit.test_reader_never_confirms_a_claim_whose_push_was_rejected
- StorageReaudit.test_reader_survives_refused_claim_unlinking_a_rotated_segment

Only pause/resume boundaries are instrumented; accepted/refused Git pushes and show processes are real. Locations: [view](bp:834), [journal loading](bp:422), [take_back](bp:1245).

Recovery introduced mutable marker state and journal removal into a design whose readers assume append-only files. Readers need a coherent snapshot or revision protocol. Reading markers twice and comparing them is insufficient: an entire failed attempt can appear and disappear between two empty-marker reads. A shared read lock is a correctness option with the documented latency tradeoff; no incomplete lock-free patch is proposed.

### R05 — Medium under corrupt input: duplicate handling depends on arrival order

**Trigger:** the same valid UUID appears as both a valid create and an envelope-invalid variant whose op is a list, placed in another machine journal.

**Expected:** both orders quarantine the ambiguous ID and produce the same state. **Actual:** malformed-first installs an invalid placeholder, then quarantines the valid copy; valid-first keeps the valid event and merely reports the malformed copy. One order exports no issue, the other exports the issue.

Reproduction: ReplayReaudit.test_malformed_duplicate_order_does_not_change_projection. Location: [Journal.add](bp:378).

This breaks the event-set/order invariant for corrupt duplicates. The physical loader sorts paths; this is not evidence that two healthy replicas with identical files spontaneously diverge. Classify all raw variants by ID before choosing validity/provenance, then quarantine consistently. No untested local workaround is offered.

### R06 — Medium under corrupt input: an orphan takeover fences another issue's close

**Trigger:** a hand-written online takeover targets a nonexistent issue but names a real existing claim as its predecessor.

**Expected:** an event that applies to no issue cannot change that other issue's ownership. **Actual:** the pre-pass adds the real claim to superseded before discovering the takeover is an orphan. The genuine owner's close is subsequently stale; its issue remains in progress with the original claim.

Reproduction: ReplayReaudit.test_orphan_takeover_does_not_fence_another_issues_close. Location: [superseded pre-pass](bp:640).

Validate predecessor operation, issue identity and causal relationship before using it in ownership bookkeeping. This is semantic corrupt-input handling; ordinary accepted commands did not produce the payload. The handwritten offline-takeover, quarantined-takeover and newer-version controls pass.

### R07 — Medium under corrupt input: quarantine can trap the whole causal tail

Create C has descendant D. A conflicting variant of C names D as its dependency. effective_deps unions the present causes of both C variants, constructing C → D → C.

**Expected under the explicit accepted policy:** quarantine C alone; descendants do not wait on that quarantined event. **Actual:** both C and D remain pending. The conflicting ID is not reported in integrity because the reporting pass visits only ordered events. Later normal writes depend on the held frontier and also wait.

Reproduction: ReplayReaudit.test_quarantined_variant_cannot_hold_descendants_in_cycle. Location: [effective_deps](bp:430). The existing missing-cause quarantine regression passes; this is its present-but-cyclic-cause boundary.

The fix requires an explicit acyclic ancestry rule for quarantine placeholders. Clearing every dependency blindly can create journal-chain breaks or apply children before their create; no such patch is proposed.

### R08 — Medium under corrupt input: payload validation still permits crashes and partial writes

Four distinct inputs exercise the same incomplete-validation/atomic-application boundary:

| Input | Expected | Actual / reproduction |
|---|---|---|
| Unknown-op event with UUIDv7 ffffffff-ffff-7000-8000-000000000000 | Inert event, valid issue inspectable | event_time raises year-out-of-range ValueError before checking inertness; ReplayReaudit.test_invalid_timestamp_is_scoped_even_when_event_is_inert |
| actor.thread is a list | Scoped integrity report | last_by_thread indexing raises unhashable-list TypeError outside the apply catch; test_non_scalar_actor_thread_is_scoped |
| set fields includes title plus internal reg=null | Reject entire event and preserve original title/registers | Earlier title change applies and internal state is writable; test_malformed_set_is_atomic_and_cannot_overwrite_internal_state |
| label_add labels contains a valid string followed by an object | Reject entire event | Integrity reports the later failure, but the first label remains applied; test_partially_invalid_label_add_applies_nothing |

Locations: [payload validation](bp:579), [pre-application processing](bp:647), [apply catch](bp:660).

The broad malformed-envelope batches pass; nested/scalar validation and internal field restrictions remain incomplete. Validate the full operation before mutation, restrict writable field names and types, and keep invalid/inert records away from unsafe timestamp/identity operations. Catching more exceptions alone does not undo partial state.

### R09 — Medium under corrupt input: a scoped null record disables later sync

Append the valid JSON line null to the own journal. Local info reports one integrity entry and show still works. The first sync succeeds and publishes those bytes. The next sync crashes in Link.merge while extracting remote-own IDs with e.get on None.

**Expected:** corruption remains scoped through transport, as it was during replay. **Actual:** repeated sync and coordinated claims fail with an AttributeError traceback until the record is repaired.

Reproduction: StorageReaudit.test_invalid_own_remote_record_must_not_disable_sync. Location: [remote-own extraction](bp:1185).

The proposed type guard below passes the one targeted regression on a scratch candidate. It only repairs this transport boundary; it is not the full validator needed for R08.

### R10 — Medium: first machine-identity initialization exposes an empty file

replica.json is shared across workspaces, but writing locks each workspace separately. O_EXCL creates the destination before json.dump fills it.

**Expected:** concurrent first users see one complete identity; a killed first initializer does not leave an unrecoverable empty identity before any journal exists. **Actual:** while the first initializer is paused just after real creation, another workspace reads the empty file and crashes with JSONDecodeError. SIGKILL at the same boundary leaves an empty replica.json that makes later init/write/info operations fail persistently.

Reproductions:

- StorageReaudit.test_machine_identity_first_use_is_atomic_across_workspaces
- StorageReaudit.test_machine_identity_can_recover_from_first_use_crash

Location: [replica_id](bp:172). The tests pause actual init processes and SIGKILL only their own worker group.

Serialize initialization across the home and atomically install complete, fsynced content without allowing two creators to start using different IDs. An unconditional atomic replace with a newly generated ID would be unsafe. Recovery of an established home's corrupt identity needs a distinct policy; no automatic reset patch is proposed.

### R11 — Medium: a valid dependency chain overflows cycle scanning

A synthetic valid DAG with 1,501 issues and 1,500 blocks edges, encoded in 3,002 causal events, replays with no integrity findings.

**Expected:** find_cycles returns an empty list. **Actual:** recursive traversal exceeds Python's stack limit and raises RecursionError.

Reproduction: ReplayReaudit.test_deep_valid_dependency_graph_does_not_overflow_cycle_scan. Location: [find_cycles](bp:991), used by dep cycles. This test calls the real replay and graph function directly; it is not a separate CLI timing test.

Use iterative traversal with explicit stack/path bookkeeping. Raising the recursion limit only moves the failure threshold. dep tree has another recursive walker, but its overflow was not executed.

### R12 — Low: forced status-close through update does not publish like close

A claims X; B syncs; B runs update X --status closed --force. B reports closed with no claim. A syncs and still sees in_progress because B did not publish. The equivalent close X --force publishes when it ends any held claim.

**Expected from command parity:** equivalent transitions have equivalent publication behavior. **Actual:** cmd_update only sets ended for the owner, whereas transition sets it for any claim. B's later explicit sync resolves the difference; this is not permanent ownership corruption. README's immediate-publication guarantee explicitly discusses owners, so this is a low-severity parity gap rather than a broad violation for every forced command.

Reproduction: RootReaudit.test_forced_close_through_update_publishes_like_forced_close. Location: [cmd_update](bp:1619). The narrow diff below passes this regression plus two atomic-update controls on a scratch candidate.

### R13 — Low compatibility/documentation gap: local import renumbers existing comments

On one machine, export an ordinary newly added comment: its numeric Beads ID is 1. Import a distinct issue containing a legacy comment with numeric ID 41. Export again: the pre-existing local comment is now 42.

**Expected from README's “stable on one machine” wording:** the existing exported ID survives an unrelated later local import. **Actual:** export recalculates every new comment ID above the current global maximum legacy ID.

Reproduction: RootReaudit.test_importing_legacy_comment_does_not_renumber_existing_local_comment. Location: [export_records](bp:1069).

This extends the already documented renumbering limitation to later local imports; it is not event-identity loss. UUID event identity remains intact. Do not count the already acknowledged renumbering after remote arrival as a new bug. Either narrow the stability promise further or introduce a durable export-ID policy; no small general fix is claimed.

## What the successful checks establish

The previous executable cases are fixed on this version: all 65 previous audit tests pass, alongside all 36 author tests. That does not close the whole failure families. Missing-cause quarantine now works but cyclic corrupt variants still hold descendants; basic lost-ACK recovery works but a still-running receive-pack can accept after rollback; common malformed envelopes are scoped but nested payloads and a transport boundary remain unsafe.

The healthy replay evidence is substantial: 3,036-event journals through all 720 machine enumerations plus 16 interleaved deliveries; a new 6,000-event six-machine corpus through 36 sampled enumerations with duplicate delivery; 10,000 independently calculated ancestry comparisons; and 3,602 mixed-envelope events through 18 sampled enumerations with exactly 3,000 scoped invalid records and 600 surviving comments.

The existing 2,400-command model passed eight checkpoints with 71 accepted online claim events. The new concurrent model ran two times with six workers, 3,000 commands and ten checkpoints each. The retained standalone run ended at 1,601 events / 90 distinct accepted claim IDs; the suite rerun ended at 1,608 events / 94 accepted IDs. Different concurrent scheduling changes accepted outcomes. Both matched their own successful-command receipts, exports, details, blockers, readiness and generation model with no pending events, integrity findings, fork reports or lingering unconfirmed markers. Only expected domain errors occurred; neither new run reported retry exhaustion or remote-unreachable errors.

The new model deliberately separates editable issues from 12 ownership targets. Partitions withhold sync and replace online ownership operations with reads; they do not emulate packet loss. Its blocker oracle is independent for direct blocks edges on task-only graphs. It does not prove every forced-close/takeover race; targeted failures above remain authoritative despite the successful traffic runs.

## Compatibility, performance and design observations

All 32 available real JSONL files (3,578 records, including workspace copies) imported and round-tripped under canonical comparison: source_repo_path removed, labels/dependencies treated as sets, records ordered by ID. This is parsed-record equivalence, not raw serialized-byte equality. The 27 files br could load produced identical ready/blocked sets. Five inputs remained rejected by br both before and after bp export, including project-a and runledger. bp preserves those duplicate legacy comment IDs; it does not repair invalid br input. All 96 bv triage/plan/insights invocations returned valid JSON and exit 0. Source repositories were only read; consumers ran in scratch repositories without remotes.

Performance used 1,000 issues with later field updates in six globally chained journals. Each size had one fresh load/replay worker and three CLI show samples. Other audit work was running on this machine; this was not an isolated CPU/cache benchmark.

| Events | Load + replay | Median show | Peak worker RSS |
|---:|---:|---:|---:|
| 10,000 | 0.114 s | 0.207 s | 58.8 MiB |
| 50,000 | 0.593 s | 0.800 s | 182.6 MiB |
| 200,000 | 3.035 s | 3.105 s | 643.2 MiB |

Those measurements quantify the accepted replay cost rather than making the no-projection decision a finding. At 50k events a read is already close to a second on this workload; at 200k it costs several seconds. The 1,501-issue graph recursion failure is a separate functional issue.

With remote auto-GC explicitly disabled by process options, 1,000 one-event syncs grew the local bare remote to 8,243,612 logical bytes. One explicit GC reduced it to 785,520 bytes. A fresh first sync after GC took 0.264 s and stored 756,993 bytes in sync.git plus 400,451 journal bytes. These are local filesystem sizes, not network transfer bytes or allocated disk blocks. GC after every sync and GitHub latency/growth were not remeasured.

Two design observations are separate from the findings and from the original accepted decisions:

- Cancellation and unconfirmed markers make recovery a transaction protocol spanning the local journal, local marker file and remote ref. Each part can be individually well-formed while their combined observation or rollback is wrong. The small R03 patch is useful but does not establish the R01/R04 invariants.
- Two non-epic tasks can acquire a parent cycle through concurrent offline parent edits. Both bp and br 0.5.7 report the cycle while returning both tasks as ready; br blocked is empty. This agrees with br. README's broad “loops never ready” wording needs qualification for non-blocking parent cycles; no br disagreement is reported.

Unchanged accepted choices were exercised where relevant, not relabeled as findings: claims do not expire; agent threads own them; offline claims are provisional; in_progress is a claim; newest IDs display conflicted values; stale named closes/releases are fenced by takeover; child display keys can renumber; quarantine is intended to be local to an event; sync holds the writer lock during publication; publication uses one ref; rotation is the only compaction; local-only repositories do not sync.

|---:|---:|---:|---:|---:|
| 10,000 | 0.114 s | 0.069 s | 0.207 s | 61,685,760 bytes |
