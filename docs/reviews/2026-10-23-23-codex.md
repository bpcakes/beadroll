C1 — Medium / P2 — Unpublished-count overflow can report a failed command after committing its mutation

Location: crates/beadroll-sync/src/synchronise.rs:404–407. Responsible integration boundary: crates/beadroll/src/cli.rs:354–360, together with the commit in crates/beadroll-sync/src/tx/writes.rs:136–150.

Trigger: a remote-backed scratch store has a two-line segment and the exact string published count "-170141183460469231731687303715884105725". This is representable in the new Int. Before the write, `list --json` succeeds and reports unpublished = i128::MAX. Run `comments add KEY once --offline --json`.

Observed: the command exits 1 with empty stdout and IO, "the published counts put the unpublished count beyond what bead counts; repair it, or run `bead sync`". Nevertheless, the comment event has already been appended and fsynced: the segment grew from 522 to 776 bytes. Restoring the metadata and showing the issue confirms that the comment exists. A retry can append it again.

Root cause: the new checked subtraction/addition correctly rejects the result, but its real command caller invokes it only from `finish`, after the transaction appended its events and retired receipts. The error then replaces the successful command result. This violates R3's arithmetic-boundary requirement and makes a non-idempotent write look unsuccessful. A pre-write count alone is insufficient: this probe starts with a valid maximum count and crosses the boundary with the new event. Previously this particular 39-digit result was representable by Int and below the 4,300-digit output limit, so it did not take this newly introduced failure path.

Recommendation: reconcile this check with commit/result handling at the command/transaction boundary. If exhaustion must fail the command, validate the prospective count including staged events before committing; alternatively, preserve an already committed command's successful result and report the unavailable count as a distinct actionable warning. Apply the policy to every write passing through `finish`, not just comments. Keep checked arithmetic in `unpublished_count`.

Exposure is limited to unusual legacy or hand-edited metadata near the numeric bound; ordinary bead-written counts cannot realistically reach it. This probe does not demonstrate malformed event bytes or incomplete journal appends: the defect is a durable successful mutation reported as failure.

C2 — Low / P3 — Boolean priorities still use the retired presentation in `bead show`

Location: crates/beadroll-core/src/op.rs:81–83; omitted consumer: crates/beadroll/src/commands/show.rs:100–111, especially line 103.

Trigger: replay a supported format-1 create with priority true or false, then read it through both `list` and `show`.

Observed with the freshly built binary: true prints `[P1]` in `list` but `[PTrue · OPEN]` in `show`; false prints `[P0]` versus `[PFalse · OPEN]`. `show --json` correctly retains true/false.

Root cause: the changed IntegerField Display implementation is used by State::row, but show builds its header from the detail Object. `field(item, "priority")` calls `str_of`, which deliberately retains diagnostic-style `repr` and therefore renders booleans as True/False. The actual detail renderer bypasses the changed implementation. This leaves the intended R1 presentation change incomplete and contradicts CHANGELOG.md:18–19 and REVIEWING.md:1557–1558.

Recommendation: render the priority specifically through IntegerField's numeric display at the show-summary boundary. Preserve the stored/detail JSON boolean and the general `str_of`/`repr` diagnostic contracts. Add a CLI case for both boolean values that compares list/show text while asserting JSON remains boolean.
