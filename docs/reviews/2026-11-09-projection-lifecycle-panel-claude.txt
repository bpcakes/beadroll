## Findings

- [low] [crates/beadroll-core/src/snapshot.rs:79-84] and [README.md:265-266] Create events in a snapshot recap have no `issue()`, but the README suggests they do
  - **Root cause:** `SnapshotEvent::issue` calls `self.event.issue()` and then `issue_named`. `Event::issue` (`journal/event.rs:249`) reads the event's `issue` field, and create events don't set it: the CLI writes `tx.emit("create", None, …)` (`commands/create.rs:109`, `commands/import.rs:72`), and the test fixtures do the same. So a create event's `issue()` is always `None`, even though this snapshot's replay made that issue. The issue's uid is the create's own id (`state/issue.rs:129`).
  - **Impact:** The README says to "iterate the recap's `events()` and resolve each event's `issue()` through that same snapshot". The `issue()` doc says "only when the same snapshot's replay created it". A consumer following that guidance (pancake-studio) will find no issue for every creation event, which is one of the most common activity kinds. Nothing breaks: the CLI recap (`commands/recap.rs:219`) also leaves create titles null, so CLI output is unchanged. The new test `tree_snapshot_binds_activity_export_and_issue_resolution_to_one_read` only resolves a comment event (`eid(3)`), so nothing covers this case.
  - **Kind:** supporting obligation (contract documentation)
  - **Recommendation:** Pick one at the snapshot boundary:
    - Make `SnapshotEvent::issue` fall back to `state.issue(event.id())` when the op is a create.
    - Or keep the behaviour and say in the `issue()` doc and the README that create events must be resolved by their own id.

    Either way, add a create event to the snapshot test.
