I found one medium defect and one low documentation gap.

- [medium] [crates/beadroll-core/src/key.rs:23] Journals that used to replay can now lose imported issues whose keys end in a long number
  Root cause: `number_too_long` used to refuse a key's number only from 4,300 digits up. It now refuses any number from `i128::MAX` (39 digits) up. `create_problem` (`crates/beadroll-core/src/event.rs:410`) calls it, and that check runs everywhere a format-1 history is read: `payload_problem` in `journal/event.rs:137` and `journal/read.rs:59`, import (`import.rs:200`) and writes (`beadroll-sync/src/tx.rs:316`). Keys are strings, and bead does write keys it did not mint: `import.rs:376` uses the record's `id` as the key. So `bead import` could write `proj.123…` with 39 to 4,299 digits, and earlier Rust and Python builds replayed it as an issue.
  Impact: After upgrading, such a create is a `Trouble::Flaw` ("create event has no valid 'key'"). The issue is no longer applied, and every later event on it falls with it. Valid stored data changes meaning, which R2 forbids. The CHANGELOG says "Nothing bead writes changes: format 1 holds no integer beyond a `u64`", but a key number is text, not a JSON integer, so that guarantee does not cover this case. This is a new restriction, not a retired parity rule: before, the limit only matched what Python could print.
  Kind: substantive defect
  Recommendation: Keep key-number validity independent of `Int`, at the key boundary. In `free_key`, count on from the decimal digit string (a short increment over ASCII digits, as the old `increment` did). Then make `number_too_long` refuse nothing, or keep the old 4,299-digit boundary. `mint_key`'s `VALIDATION` refusal can stay as it is, since it only applies when a command runs. Add a replay test that a create keyed `x.<40 digits>` still applies and that its renamed duplicate counts on.

- [low] [CHANGELOG.md:9] The CHANGELOG leaves out two of the changes it retires
  Root cause: The entry does not mention three behaviour changes.
  - **Out-of-range numbers are now refused.** Numbers beyond an `i128` in `BEAD_*` settings, `--limit` and `--estimate`, which used to saturate, now give `CONFIG` or a usage error. `settings.rs:322` tests the old 60-nines value as refused now. A `COLUMNS` beyond an `i128` is now ignored, where it used to give `usize::MAX`.
  - **`GIT_CONFIG_COUNT` reads only ASCII digits.** `link.rs:116` passes `is_digits`, which now accepts ASCII digits only. A count like `٣` was read as 3; it now reads as zero, or `CONFIG` when no settings are carried over. `docs/REVIEWING.md` covers this change; the CHANGELOG does not.
  - **A large or overflowing published count in `meta.json` now gives `IO`.** A float such as `-1e44` that used to produce an unpublished count now gives `IO` "is not a number". The CHANGELOG half-states this as "`meta.json` count beyond it `IO`".
  The doc comment at `beadroll-git/src/env.rs:112` still says "Unicode digits".
  Impact: Users see an undocumented change on upgrade; R3 asks for each dropped rule to be documented.
  Kind: supporting obligation
  Recommendation: Add these to the CHANGELOG entry and fix the `CountRules` doc comment.

The other changes check out:
- **Conflict values in `bead show`:** they now print as raw UTF-8 JSON, which is safe because `cli/output.rs:78` (`visible`) escapes control and bidi characters on all human output.
- **Generation and legacy-id overflow:** the fallbacks in `claims.rs`, `ownership.rs` and `export.rs` cannot be reached with input bead reads.
- **Count arithmetic:** the checked arithmetic in `unpublished_count` and `active_segment` returns the established `IO` errors.

## Requirement coverage
- **R1: satisfied.** The 4,300-digit `Int` arithmetic is replaced by a checked `i128`. The Unicode digits and underscores in `text/number.rs` are gone, and `decimal_value` has no callers left. A boolean priority prints as `1`/`0` (`op.rs:83`) and `show` prints conflicts as JSON (`show.rs:237`). `repr` and `repr_str` still quote diagnostics, and none of the changed paths touch the stress RNG.
- **R2: unmet.** Format-1 bytes are unchanged, and overflow returns `None` and becomes `VALIDATION`, `IO` or `CONFIG` rather than wrapping. But valid imported histories with 39–4,299-digit key numbers no longer replay (finding 1).
- **R3: partially met.** `REVIEWING.md` §2, `FINDINGS.md` U07/S02 and the subject tests are updated (`port_alignment.rs`, `short_fields.rs`, `pending.rs`, the golden `tracker.txt`, parse and settings tests). The CHANGELOG has the omissions in finding 2. I did not run the baseline, as the constraints asked.
- **R4: satisfied.** Core stays pure, no new dependencies, and output is deterministic.

## Open questions
- Did the maintainer mean to shrink valid key numbers to fit an `i128` for existing histories as well as new writes? Only "refused at creation" is written down, and that reads as covering new writes only.

## Test gaps
- No test shows that an existing journal with an imported create keyed beyond an `i128` still replays. `u07_…` (`port_alignment.rs:186`) only pins the new refusal, so the regression in finding 1 is enshrined, not caught.
- No test in either version covers `GIT_CONFIG_COUNT` written in non-ASCII digits. A change that silently overwrites a caller's `GIT_CONFIG_KEY_0` when settings are carried over would not be caught. This matters less, because git itself refuses such a count.
