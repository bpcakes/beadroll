## What I checked

- **Claim-exhaustion retry loop (`crates/beadroll-core/src/replay.rs:83-134`):**
  - **It stops.** Each retry adds at least one new inert entry (`:119`, `:125`). There are only so many events, so the loop ends.
  - **The detection rule is sound.** A claim's generation can only be raised by a claim (`claims.rs:47`); a create sets it to 0 (`create.rs:136`). Each applied claim adds at most one to the largest proposed generation. So "some proposed generation plus the number of events passes an `i128`" (`replay.rs:86-90`) catches every history that could run out.
  - **State resets properly.** `apply_all` consumes `applying` with `Option::take` (`:305`), and both `st` and `applying` are restored from the saved copy before each retry (`:132-133`).
  - **The AE01 fix holds.** `awaiting` now carries over across retries (`:97`), even though `settle_takeovers` skips takeovers already marked inert (`:253`).
  - **One leftover is out of scope.** An early return on `KeySpace` now skips `st.knowledge = knowledge`, but `st` is thrown away on that path anyway.
- **Claim boundary (`claims.rs:35-39`):** exhaustion is caught before `end_claim` or any change to the issue. `apply.rs:105-116` records it under `integrity` and reports the claim as not applied. `ownership.rs:100-109` returns `VALIDATION` before the claim is emitted.
- **Keys (`key.rs`):** `free_key` strips leading zeros the same way the old `Int::from_parts` did, so `x.007` still renames to `x.7`. `next_number` carries correctly into a new digit. `number_too_long` still counts every digit, leading zeros included, against the 4,300 limit, as before.
- **Number parsing (`text/number.rs`):**
  - `trim()` uses Rust's whitespace set, which does not include `\u{1c}`–`\u{1f}`, so the existing "refused" cases still hold.
  - `strip_prefix(['+','-'])` plus `is_digits` rejects `+-1`, `1_0` and non-ASCII digits before `i128` parsing runs.
  - Rust's `f64` parser still accepts `inf`, `infinity` and `nan` in any case, as the CHANGELOG says.
- **Callers:**
  - `settings.rs:121`, `layout.rs:63`, `commands.rs:542`, `history.rs:51` and `recap.rs:270` now use `as_i128`. Where an overflow used to saturate, it now fails to parse, which REVIEWING §2 and the CHANGELOG record.
  - `GIT_CONFIG_COUNT` (`link.rs:114-116`, `env.rs:158-163`): digit-only text that overflows an `i128` makes `int` return `None`, which becomes `ConfigCount`. This matches the documented behaviour.
- **Conflict display (`show.rs:235-239`):** it uses `Format::COMPACT` with `ascii: false` (`write.rs:32-35`). Non-ASCII text stays readable, and the golden file matches. The `Debug` fallback only runs if the write fails, which a parsed value cannot trigger.
- **Projection codec (`codec.rs:286-289`, `:523`):** integers beyond an `i64` round-trip as text through `Int::parse`. Every `i128` survives the round trip.
