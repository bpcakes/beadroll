Finding C1 — low — Claim overflow silently reuses the previous generation

Location: crates/beadroll-core/src/replay/apply/claims.rs:31–35; the corresponding command fallback is crates/beadroll/src/commands/ownership.rs:100–104.

Trigger: an in-process caller supplies a native Journal containing an accepted online claim with Value::Int(Int::from_i128(i128::MAX)), releases that claim, and claims the same issue again. The public event validator accepts the integer generation (event.rs:393–394 and is_int at 205–207). Journal::add and replay accept these native values without a JSON round trip.

Root cause: the newly fallible plus_one is converted back into the old generation with unwrap_or_else. Replay then installs a different claim ID with that same generation and reports no integrity problem. The command writer uses the same fallback. This is saturation, despite the new documented rule that a count exceeding i128 is refused, and violates R1/R2's checked-caller and structured-overflow requirements. The previous owner is ended before the overflow is checked in replay.

Observable reproduction: a read-only Rust probe was compiled from stdin against target/debug/deps/libbeadroll_core-20618b297c7b4b49.rlib, using rustc --edition=2024 -L dependency=target/debug/deps --extern beadroll_core=target/debug/deps/libbeadroll_core-20618b297c7b4b49.rlib -o /tmp/beadroll-pr46-review-l880bxut/claim-boundary-probe -. Its five events were all on replica a with actor {agent:test,thread:a}, sequenced in one journal, each depending on its predecessor. IDs were 019a5555-5555-7000-8000-000000000001 through ...005: init(prefix ex), create(key ex-1,title t), claim(generation i128::MAX), release(claim ...003), claim(empty data). Every event passed payload_problem. Replaying the first three and all five events produced:

    events=3 generation=170141183460469231731687303715884105727 claim=019a5555-5555-7000-8000-000000000003 integrity=[]
    events=5 generation=170141183460469231731687303715884105727 claim=019a5555-5555-7000-8000-000000000005 integrity=[]

Compilation and execution exited 0. The observable problem is the accepted new claim with an unchanged generation and no error; this probe does not demonstrate two simultaneous owners or a lost issue.

Counterevidence and severity: serde_json only produces exact i64/u64 integers, so ordinary serialized histories cannot directly seed i128::MAX. No practical ordinary-CLI route to this boundary was demonstrated. That substantially limits exposure and is why this is low severity, despite the explicit arithmetic contract. The native core interface does expose this boundary and currently accepts it as valid.

Recommendation: handle exhaustion at the claim application boundary before end_claim or other mutation, reporting it through an established structured error/integrity mechanism. At ClaimStep::run, map a failed increment to a structured Failure before emitting the claim instead of reusing the old generation. Cover a maximum-generation native journal, including release/reclaim or takeover, and assert that rejection leaves the previous state intact. Do not rely on a JSON fixture for this boundary because the parser changes that value to a float.
