# Independent audit of the bp tracker POC

Audit date: 2026-10-06. Implementation reviewed: `bp` SHA-256 `52273a9d909cb81e4a63608386dcf0ea7402d14ad2db0b9c91d1514821b5d5d4`. Read order: README, all of bp, then test_poc. Runtime: Python 3.14.7, macOS 26.6.2 arm64; installed br 0.5.7 and bv 0.25.0. This did not exercise the advertised minimum Python 3.12 specifically.

## Assessment

The healthy-journal convergence and conditional online claim design survived the expanded tests. The implementation does **not** yet preserve those guarantees through ordinary crash recovery: a lost claim acknowledgement followed by local work forks the writer's journal, and a torn append followed by another successful write makes the tracker unreadable. Fork handling also publishes a foreign corrupt copy, while a copied machine identity can evade fork detection by rotating differently and silently erase a concurrent field value.

These are reproducible implementation failures, not objections to persistent claims, single-ref serialization, local owner closes, or the other accepted choices. The recovery protocol and the assumptions behind version-vector ancestry need work before this POC supports the stated fault model.

The report groups the failures into **19 findings**. Several involve malformed input and explicitly say so; they should not be mistaken for divergence between healthy replicas. No original implementation, README or baseline tests were edited. Proposed diffs are review artifacts only.

## Reproduce

From `~/Documents/beads-poc`:

```sh
python3 -m unittest -v test_audit
```

Every bp subprocess in the suite sets a scratch BP_HOME and runs in a created repository or uses BP_WORKSPACE. The suite deliberately fails against the unmodified POC: bug tests assert the intended safe outcome and have no expectedFailure markers. It also reruns the 2,400-operation model, so allow several minutes. `test_audit.py` includes the randomized model; its real-data matrix calls the retained `compat_real.py` helper in the scratch directory and skips explicitly if that helper or br/bv is unavailable. Filesystem fixtures clean themselves up unless the standalone benchmark explicitly retains them.

To run one reproduction, use `python3 -m unittest -v test_audit.CLASS.METHOD` with the class/method listed in a finding. Standalone source modules and all scripts/logs are retained in `/tmp/bp-audit.GXC6hk`.

## Findings, ranked by impact

The first group concerns corrupted synchronized state, loss of access to acknowledged work, or erased conflict information; the next concerns ownership/readiness; the final group concerns robustness and CLI behavior. High severity describes impact, while each finding separately identifies whether its trigger is ordinary use, a crash, copied identity, or hand-written malformed data.


Final unchanged-source audit result: **65 tests in 471.695 s: 38 passing methods, 27 failing bug methods, 28 failing assertions (one method has two workspace-path subtests), zero errors and zero skips.** The baseline separately passed 26/26. Full logs: combined-tests.log and baseline.log. This is a completed failing audit, not a green test run.


### A01 — High: lost claim acknowledgement plus local work creates a fork sync cannot recover


Reproduction: `SyncAudit.test_bug_local_write_after_lost_ack_must_not_fork_accepted_claim`.

1. A initializes and publishes an issue. B syncs.
2. A runs `BP_TEST_CRASH_AFTER_PUSH=1 bp claim ISSUE --json`; exits 99 after remote acceptance, before local append.
3. A runs `bp comments add ISSUE 'local work after lost acknowledgement' --json`; succeeds.
4. B syncs and sees A's accepted confirmed claim.
5. A runs `bp sync --json`; fails `JOURNAL_FORK`, claiming the machine identity was copied although it was not.

Expected: recover the accepted claim and retain the acknowledged comment. Actual: remote claim and local comment occupy divergent suffixes of the same own segment. Retrying sync cannot reconcile them. The baseline only retries the claim immediately, with no intervening local writes. Normal continued local work after a push timeout/crash hits this gap.

`coordinated` publishes unpersisted `tx.pending`, appends it only after acknowledgement, and leaves no durable indication that the journal's next position is reserved. `writing` can then reuse that position. A fix needs a durable pending-operation record before attempting the push and recovery before any subsequent append, with the claim withheld from projection until acceptance is established. Blindly appending claims before pushing would violate the claim protocol. No complete patch proposed for this protocol change.

The same gap can arise if local append/fsync fails after remote acceptance; that specific second route was not separately run.


### A02 — High: reporting a foreign fork is followed by publishing the corrupt variant


Reproduction: `SyncAudit.test_bug_foreign_fork_report_must_not_replace_published_journal`.

1. A publishes an issue; B syncs it.
2. In B's copy of A's journal, change the create event title, preserving valid JSON and the event ID.
3. B runs `bp sync --json`.

Expected: retain/report the fork without replacing the authoritative remote file. Actual: sync exits zero and includes the file under `forked_journals`, but then pushes B's rewritten foreign journal. A's next sync fails `JOURNAL_FORK`; a fresh C sees the forged title. Supplementary observed output is in `sync-impact.json`.

`Link.merge` records a foreign fork and leaves the local version in place. `Link.publish` unconditionally builds its tree from those local files. Thus a corruption report is followed immediately by propagation of the corruption, and peers with different copies can keep republishing their competing variants. Git ancestry retains older blobs, so this is corruption of the current synchronized projection and loss of convergence, not a claim that every historical object has been erased.

A small fail-closed proposed fix is `foreign-fork-fix.diff`. It rejects publication when `Link.merge` has found any foreign fork, identifies the paths in `JOURNAL_FORK`, and preserves both existing files. The changed behavior returns an error instead of a successful sync report. The one relevant regression was run against a scratch patched copy and passed (1 test, 1.060 seconds). No original file was modified. The patch was not tested against the full baseline suite.

```diff
--- a/bp
+++ b/bp
@@ -998,6 +998,9 @@
     def publish(self, tip: str | None, extra: list[dict] | None = None, note: str = "sync") -> tuple[bool, str | None]:
         """Conditional update: the new commit's parent is the head we fetched, and the push is a
         plain fast-forward, so the remote refuses it if anyone else got there first."""
+        if self.forks:
+            raise BpError("JOURNAL_FORK", "refusing to publish divergent foreign journals: "
+                          + ", ".join(self.forks))
         tree = self.tree(extra)
         if tip and self.git(["rev-parse", f"{tip}^{{tree}}"]) == tree:
             return True, tip
```


### A03 — High: the next acknowledged write turns a torn tail into replay failure requiring manual repair


Reproductions:

- `SyncAudit.test_bug_torn_tail_followed_by_successful_append_must_stay_readable` — direct partial-tail bytes.
- `SyncAudit.test_bug_file_size_limit_partial_append_must_not_poison_next_write` — actual OS `RLIMIT_FSIZE` caps a create append at the existing segment length + 100 bytes; description is 100,000 characters.
- `SyncAudit.test_bug_kill_mid_append_then_successful_write_must_stay_readable` — actual SIGKILL after an instrumented file wrapper writes and flushes the first 100 bytes of the original `append_events` write. The wrapper makes the interruption deterministic; it is not a naturally timed kill of an uninstrumented kernel write.

Expected: completed events remain readable, and later acknowledged writes remain readable/syncable. Actual: reads initially succeed because `read_segment` ignores the invalid unterminated final line. The next `create` returns zero and prints the new issue; its bytes were appended directly to that partial line. Every following replay reports `CORRUPT_JOURNAL` at line 3. `sync` fails before fetching, because it replays to count known renames first. Acknowledged later work is inaccessible along with the earlier tracker until manual journal repair.

The reader's torn-tail tolerance is correct by itself; the writer needs an explicit incomplete-tail recovery policy while holding the lock, and publication must not spread incomplete tails. Preserve damaged bytes for diagnosis, distinguish complete non-newline JSON from incomplete JSON, and reconcile an already-published tail before reusing its position. No incomplete repair patch is proposed: naïve truncation can itself violate the remote prefix rule if the partial tail was already published.


### A04 — High: segment boundaries hide a copied-machine fork and version vectors invent ancestry


Reproductions:

- `SyncAudit.test_bug_copied_machine_id_fork_across_segments_is_detected`.
- `SyncAudit.test_bug_segment_boundary_fork_must_not_erase_concurrent_title`.

1. Initialize/create/sync A; copy its entire BP_HOME to a second scratch machine.
2. Set A's `BP_ROTATE_BYTES=1`; set the copy's `BP_ROTATE_BYTES=1000000`.
3. Copy updates the title first, appending old segment 000001. A updates the title second, starting segment 000002. Both updates name only their common predecessor.
4. A syncs; copy syncs.

Expected: detect the copied-machine fork, or at least preserve the two concurrent title values. Actual: sync succeeds with `forked_journals=[]`, `waiting_events=0`, and `integrity=[]`; the later A title replaces the copy's title with no `conflicts` entry. Both physical events remain present. A's following sync converges to this incorrect projection.

Per-file prefix comparisons miss a fork split over two segment files. `State.saw` uses physical per-machine sequence positions as ancestry without validating the predecessor chain, so the later segment's event falsely appears to have seen the copy's earlier-segment event. This is a real CLI route to the same invariant violation covered by the replay audit's handwritten-event tests. Enforce chain continuity across the complete machine journal, not just byte-prefix compatibility per segment; do not manufacture causal dependencies from file order.

`State.saw` (bp:381) treats seeing position N in a journal as seeing every prior position. Handwritten events can violate that premise: priority=1 from machine A; a later A comment depending only on create; B priority=4 depending on that comment. Expected: A's and B's priority writes are concurrent (or the invalid chain is explicitly rejected). Actual: `saw(B, A-write)` is true, priority=1 is silently retired, and no integrity entry reports the malformed chain.

A related fixture puts a missing-cause comment before a confirmed claim in one journal, while the claim names only create. Expected: reject the broken chain or hold the later claim. Actual: the predecessor stays pending and the later claim becomes confirmed.

Reproductions: `ReplayAuditBugs.test_non_chain_same_journal_must_not_invent_ancestry` and `ReplayAuditBugs.test_non_chain_claim_cannot_bypass_pending_predecessor`.

The sync reviewer independently found a CLI-only trigger: copied BP_HOME identities using different rotation thresholds write divergent continuations into different segment numbers. Prefix checks never compare those events as a fork. Their `SyncAudit.test_bug_copied_machine_id_fork_across_segments_is_detected` is the primary reproduction for this finding; these tests isolate its replay consequence.

No small validated patch is proposed. The optimization needs verified per-journal predecessor ancestry, including across segment boundaries, plus a deterministic treatment of violations; inventing a predecessor dependency after loading would hide rather than report the copied-machine fork.


### A05 — High under corrupt input: quarantined takeover changes ownership and projection by delivery order


The `superseded` pre-pass (bp:478) includes events later skipped by quarantine. Fixture: a valid online owner; two conflicting payloads for one later event id, one an online takeover and one a comment; then the valid owner's close naming its original claim. Expected: only the duplicate event is inert, the close succeeds, and reversing duplicate delivery changes nothing. Actual: takeover payload first causes the close to be listed as stale and keeps the old owner in progress; comment payload first closes normally. Both replays have the same complete multiset of event payloads.

Reproduction: `ReplayAuditBugs.test_quarantined_takeover_cannot_supersede_a_valid_close` explicitly builds both orders and compares complete exports and details before checking that the owner ended.

Boundary: this is a malformed/conflicting journal case exercised through `Journal.add`. The ordinary disk loader sorts directory and segment names, so identical physical files at identical paths choose the same first variant. The bug breaks the stated event-set/enumeration-order invariant and means the supposedly quarantined event influences legitimate ownership; it is not a claim that ordinary healthy sync randomly reorders identical paths.

Proposed diff: `proposed-quarantined-takeover.diff`, excluding quarantined ids from the pre-pass. The test passes with that change.


### A06 — Conflict correctness under malformed placement: an identical duplicate changes journal identity


Machine A writes priority=1; machine B writes priority=4 concurrently. Copy A's identical event into B's physical journal before B's event. Enumerate A first: both priority values survive as a conflict. Enumerate B first: `Journal.add` assigns A's id to B's sequence, and B's concurrent priority write silently retires it. `Journal.add` deduplicates by event id without validating the physical journal against `event.replica` (bp:321).

Expected: either explicitly reject/quarantine the misplaced copy or obtain the same projection for identical payloads regardless of journal enumeration. Actual: same event set, different conflicts, no integrity report. Reproduction: `ReplayAuditBugs.test_identical_id_in_different_machine_journals_is_order_independent`.

Boundary: this test directly controls Journal.add enumeration and deliberately places an event in the wrong machine directory. With the same healthy files at the same paths, `load_journal` always sorts paths. This is malformed-input robustness and an event-set invariance gap, not a demonstrated natural divergence between two healthy fully synchronized copies. Validate event provenance and journal-chain consistency before using physical positions for version vectors. No partial source patch is proposed.


### A07 — High storage isolation: repository-controlled workspace ids escape BP_HOME


Location: `Workspace.__init__`, bp:93; `find_workspace`, bp:147. The id is concatenated directly with `BP_HOME`. An absolute id replaces the base path; `../...` escapes it. A `.bp.json` in a checked out branch can direct normal tracker writes into the checkout or another accessible location. This violates the storage boundary, and can collide with an unrelated tracker. This is not the accepted choice to route workspaces by tracked config: a workspace id is being accepted as an arbitrary filesystem path.

Reproduction: `CompatAuditCLI.test_workspace_config_cannot_escape_home`. Write `.bp.json` with `{"workspace":"/absolute/scratch/escaped"}` or `{"workspace":"../escaped-relative"}`, then run `bp init --prefix evil --json` with scratch BP_HOME. Expected CONFIG refusal. Actual exit 0; events/lock/meta are created outside BP_HOME. Both test destinations remained inside disposable scratch and were cleaned up.

Proposed unified diff: `compat-proposed.diff` validates opaque workspace ids before constructing paths. Proposed only; not applied or regression-tested as a fix.


### A08 — Ownership: distinct agent threads share the truncated owner identity


`actor_label` (bp:240) abbreviates the thread, and claim/release/close authorization compares that abbreviated label. On the same machine, claim with thread `01a0c450-0001-7000-8000-000000000001`, then release with `01a0c450-0002-7000-8000-000000000002`. Both are valid UUIDv7 values. Expected: NOT_OWNER. Actual: exit 0, ownership released by the second thread.

Reproduction: `ReplayAuditThreadOwnership.test_distinct_threads_with_shared_first_eight_characters_are_not_same_owner` runs these commands against a real local bare coordination remote, not merely a replay fixture. The current harness's CODEX_THREAD_ID and CODEX_SESSION_ID were inspected only for UUID version; both are version 7. The actual identifiers were not printed or retained. UUIDv7's first eight hex characters contain the high 32 bits of a 48-bit millisecond timestamp; sessions in the same 65.536-second bucket share those eight characters. This is a plausible ordinary-session collision, not just an artificial UUID4 collision.

Proposed minimal diff: `proposed-full-thread-owner.diff`. Using the full thread in the label fixes the demonstrated comparison without changing stored raw event identity. A fuller implementation could keep abbreviated display labels and introduce separate exact owner keys. Explicit `--actor NAME` identity remains the deliberate override in this proposal.


### A09 — Ownership/readiness: generic status updates bypass claim guards


Location: `cmd_update` at bp:1282 and `cmd_ready` at bp:1411. Claim an issue as `owner-thread`; `close` from `other-thread` correctly fails with CLAIMED_BY_OTHER. The same other thread can run `update ISSUE --status closed --json` successfully. The closed issue still has its confirmed claim. `update ISSUE --status open` also succeeds and then `ready` offers the still-claimed issue.

Expected: status changes on a claimed issue respect the ownership/transition checks, and ready work has no live confirmed owner. Actual: the generic set path writes the status without the transition's owner check, claim reference, claim ending, or immediate publication. It consequently bypasses the fencing attached specifically to named close events as well; the two regression tests exercise the direct guard and readiness failures, not every delayed-status/takeover interleaving.

Reproductions: `RootAudit.test_nonowner_cannot_bypass_close_guard_with_status_update` and `RootAudit.test_claimed_issue_is_not_ready_after_nonowner_status_update`. Both fail by ordinary CLI commands against a local coordination remote. This is separate from the accepted design for owner `close`: that path emits a close naming the exact claim, whereas this one emits a generic set.

Proposed remedy: validate status transitions through one ownership-aware path, preserving claim references and the documented transition semantics; make ready additionally reject a live confirmed claim. Merely hiding the issue from ready does not fix the unauthorized close or stale write. No partial patch is offered as a complete fix.


### A10 — Ownership/false failure: a claiming update commits before validating its remaining edits


Location: `cmd_update`, bp:1287. `claim_issues` commits before the rest of update is validated. `bp update ISSUE --claim --parent missing --json` returns `ISSUE_NOT_FOUND` / exit 1 but has already acquired and published a confirmed generation-1 claim. No title/parent edit is applied. Scripts treating failure as no change leave the issue owned unexpectedly.

Reproduction: `CompatAuditCLI.test_claiming_update_validates_parent_before_committing_claim` creates a local bare remote and synthetic issue, executes the above, then shows the issue. Expected no claim after validation failure; actual claim mode online remains. Suggested remedy: validate all update fields/targets and stage the edits with the claim inside one coordinated build; a validation-only preflight fixes this repro but does not make the two separate transactions atomic. No partial patch proposed.


### A11 — Wrong readiness: the second parent's blocker is ignored


A child has two parent-child edges, first to a free parent, second to a parent held by a prerequisite. Expected: the child is blocked by the second ancestry path. Actual: `parent_of` returns only the first parent and `open_blockers` follows only that chain (bp:750, bp:762), so the child appears ready. All edges are supported inputs; concurrent parent changes can preserve multiple parent edges under the accepted add-wins rule.

Reproduction: `ReplayAuditBugs.test_second_parent_blockers_hold_child`. The compatibility reviewer independently ran the same synthetic records through the installed `br`: br imports them, excludes au-one from ready, and includes it in blocked; bp includes au-one in ready and omits it from blocked. See `compat_multiparent.py` and `compat-multiparent.log`.

Proposed diff: `proposed-all-parent-blockers.diff`. Traverse every parent edge while retaining cycle protection and the existing rule that a done ancestor stops that path. This fixes readiness only; `detail.parent` and `list --parent` still expose only one parent, so the proposal is not a complete redesign of multi-parent display/filter semantics.


### A12 — Compatibility identity: exported integer comment ids change between exports


Location: `export_records`, bp:862–870. IDs are reassigned from the current sorted event-id set on every export. A first comment at UUID time 3000 ms exports as integer 1; a causally later comment with time 2000 ms exports as integer 1, and the first becomes 2. The journal comment ids remain immutable, but the interoperability ids do not. This can also happen when an earlier remote comment arrives after a local export, or when importing a higher legacy integer.

Reproduction: `CompatAuditCommentIds.test_existing_comment_export_id_survives_clock_skewed_new_comment` uses a legal single-journal causal chain with a clock rollback. Expected first comment to keep id 1; actual 2. Same complete event set still produces equal ids on every replica; the defect is identity stability between exports. A stable integer mapping needs a defined allocation/collision policy compatible with imported legacy ids; no unsafe hash/truncation patch proposed.


### A13 — Quarantine robustness: a conflicting event with a missing cause holds descendants


One event id has two payloads: its first payload depends on a missing cause, its second depends on a present create. A valid subsequent field edit depends on that event id. Expected under the hand-off's explicit decision: quarantine only the conflicting event; nothing waits on it. Actual: both the duplicate and its descendant remain pending, no integrity entry is emitted for the pending duplicate, and the edit never applies.

Reproduction: `ReplayAuditBugs.test_quarantined_event_with_missing_cause_does_not_hold_descendants`. The chosen-first-payload causal graph is built before quarantine handling. No source diff is proposed because bypassing all dependencies naïvely can apply a descendant before a needed create when clocks are skewed; the causal placeholder policy needs an explicit design and tests.


### A14 — Robustness: malformed events crash replay; unknown versions and operations execute silently


One valid JSON line can prevent replay of every unrelated issue. Eight cases were checked: JSON array; missing id; missing op; missing replica; non-UUID id; integer dependency; object dependency; array-valued data. Seven cause uncaught TypeError, KeyError, ValueError, or AttributeError in loading/replay. Integer deps silently remain pending without an integrity report. This is scoped to the replay/storage boundary; this test does not claim every CLI path's JSON error envelope was checked here.

A `v:999` set operation is applied as if it were version 1. An unknown operation on an existing issue silently changes updated_at and produces no integrity warning, despite its semantics being unknown.

Expected: explicitly report/reject unsupported formats, and scope a malformed event so unrelated valid state is still inspectable. Actual: unvalidated events execute, silently vanish into pending, or crash replay. Reproductions: `ReplayAuditBugs.test_bad_event_schema_has_scoped_damage`, `test_unknown_event_version_is_not_applied_silently`, and `test_unknown_operation_is_reported_and_does_not_mutate_timestamp`.

No superficial catch-all patch is proposed. Validate envelope types, supported version/op, UUID identifiers, dependency types, payload schemas, and physical journal identity before sequence indexing/replay. An integrity path should preserve evidence without applying unknown semantics.


### A15 — Robustness: an accepted comment id of zero breaks export


Location: `export_records`, bp:889, and `detail`, bp:839. `legacy_id or ...` treats integer zero, accepted by bp import, as absent. Import succeeds, but export reaches `new_ids[None]` and raises `KeyError: None`, with a traceback instead of JSON error handling.

Reproduction: `CompatAuditCLI.test_imported_comment_zero_id_roundtrips` imports a synthetic comment `{"id":0,"author":"audit","text":"zero","created_at":"2026-01-01T00:00:00Z"}`. Expected zero preserved; actual export exit 1 and traceback. A later independent br0.5.7 probe also rejects a complete zero-comment record with SYNC_CONFLICT, so this is bp accepted-input robustness rather than an established valid-Beads-record compatibility failure (compat_comment_zero_br.py and compat-comment-zero-br.log). The same underlying path also affects a missing/null legacy id, which needs separate input validation/allocation. Proposed diff fixes the zero-id truthiness error using an explicit None check; it does not claim to fix missing ids.

A separate complete-record probe through br 0.5.7 also rejects comment id 0 with SYNC_CONFLICT. This establishes an accepted-input/export robustness bug in bp, not that zero is a supported Beads interoperability id. Probe: compat_comment_zero_br.py and compat-comment-zero-br.log. Missing/null comment ids were not separately reproduced.


### A16 — Identity robustness: missing ps crashes nested harness detection


Location: `nearest_harness`, bp:201. With both `CLAUDE_CODE_SESSION_ID` and `CODEX_THREAD_ID` present, an unavailable `ps` raises uncaught `FileNotFoundError`. Even `bp info --json` fails with a traceback.

Reproduction: `CompatAuditIdentity.test_missing_ps_does_not_crash_nested_actor_detection` runs an actual bp subprocess with scratch PATH containing only python3/git symlinks and both synthetic session variables. Expected the existing fallback to Codex identity; actual exit 1. This is an actual missing executable test, not only a mock. `compat-no-ps.log` retains output. Proposed diff returns None on OSError, enabling the existing fallback.


### A17 — Identity configuration: BP_THREAD alone fails to override detection


Location: `detect_actor`, bp:220–234. README says BP_AGENT, BP_THREAD and --actor override detection, but BP_THREAD is read only when BP_AGENT is also present. Under CODEX_THREAD_ID=detected and BP_THREAD=override, the event thread stays detected.

Reproduction: `CompatAuditIdentity.test_bp_thread_overrides_detected_thread_without_bp_agent`. Expected codex/override; actual codex/detected. Proposed diff applies BP_THREAD after selecting agent/thread.


### A18 — CLI data handling: global flags consume operands after --


Location: `main`, bp:1716–1727. `bp create -- --json` should create an issue literally titled `--json`. Global preprocessing removes the value despite the end-of-options marker, then reports a missing title in JSON. The same preprocessing also targets literal `--actor` operands and values.

Reproduction: `CompatAuditCLI.test_global_options_respect_end_of_options`. Expected success/title preserved; actual exit 1 VALIDATION. Remedy: split at the first `--`; extract global flags only from the preceding option portion, preserving the tail for argparse. No diff here because blindly removing globals can also consume option argument values and deserves one parser contract.


### A19 — CLI automation: parser errors bypass the JSON error envelope


Location: `main`, bp:1728. `bp show --json` returns argparse human usage on stderr, exit 2. Domain failures return JSON error/code on stderr, exit 1. Automation therefore needs two parsing modes for errors even after explicitly selecting JSON.

Reproduction: `CompatAuditCLI.test_parser_error_json_envelope`. Expected error JSON; actual human usage text. Remedy: custom ArgumentParser.error raising a structured usage exception inside the same formatting boundary, preserving exit 2. No speculative broad exception catcher proposed.

## Design observations — distinct from bugs

- The conditional Git fast-forward mechanism serialized every tested claim race and prevented refused claims from entering the local journal. The gap is crash recovery across remote acceptance and local durability, not fast-forward exclusivity itself.
- A valid append-only machine chain is an essential prerequisite of State.saw's compact version-vector optimization. Segment-file prefix compatibility alone does not establish that premise. The actual copied-identity reproduction makes this an implementation obligation, not merely a theoretical concern about malicious events.
- Rollback/ref deletion can be repaired by a machine that retains the complete journal. A fresh clone of only the rolled-back remote cannot infer omitted history. Define the trust/recovery policy if administrative force updates belong to the operating model; this audit does not count that information limit as a new bug.
- Mutable Beads integer comment identities need an explicit compatibility policy. Immutability of event UUIDs does not automatically supply stable small integer ids across incremental exports.
- Import/export preserves source data, including pre-existing duplicate comment ids and user-authored paths. This fidelity means bp export does not repair all br-rejected files.
- Changing .bp.json's workspace id reroutes to a new store and leaves the original intact. No implicit migration was observed. Invalid path-like ids are the separate bug A07.

## Accepted decisions — not findings

No finding objects to non-expiring ownership/no heartbeat, thread ownership requiring takeover in a later session, in_progress being a claim, newest-event display/settlement by later edit, local immediately published owner close with superseded-claim fencing, child-key renumbering with immutable issue ids, isolating a duplicate-payload event alone, holding the lock during push, single-ref contention/retries, segment rotation without compaction/projection, or a remote-less local tracker being unable to sync. Findings A01/A04/A05/A09/A13 concern failures to implement those decisions consistently. Performance measurements describe their costs without relabeling the accepted choices as bugs.
