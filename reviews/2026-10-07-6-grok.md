## Findings

Ranked by the brief: a wrong command result or a credential in a file you are told to commit, then a split attempt or a false fork, then a dependency that comes back, then output and robustness.

### F01 — High: a failed command forgets an accepted retry

`settle_commands` (`bead` around 1719–1738) deletes every settled receipt of this actor whose text does not match the command it is about to run, and it does that before `build()` succeeds. A command that then raises — `claim missing-id` is enough — has already thrown the receipt away. The in-process `receipt` tuple in `coordinated` is not involved; this is the cross-process file.

Reproduction: `Review6.test_f01_failed_command_does_not_forget_an_accepted_retry`.

1. `update ID --claim --status closed` with `BEAD_TEST_CRASH_AFTER_PUSH=1` (remote accepted, exit 99).
2. `claim missing-id` exits 1 with `ISSUE_NOT_FOUND`. The `*.command` file is gone.
3. The same close again exits 1 with `VALIDATION` / `ex-… is closed`. One close is in the log. The retry is not recognised.

The same sequence on `update CHILD --claim --parent SECOND` exits 0 and leaves the right parent, but the log is `create, dep_add, claim, dep_remove, dep_add, dep_remove, dep_add`. The retry rebuilt the move. A different thread's failed claim does not delete the receipt, and a `sync` between the crash and the retry leaves it; both are covered by the passing receipt test.

```diff
--- a/bead
+++ b/bead
@@ -1719,7 +1719,8 @@ def command_signature(args, actor: dict, request=None) -> str:
-def settle_commands(ws: Workspace, replica: str, actor: dict, signature: str) -> bool:
-    done = False

+    """Return (already done, receipts to drop only after this command succeeds)."""
+    done, stale = False, []
```

### F02 — High: a retry in another locale rewrites or crashes an accepted description

`text_arg` uses `Path.read_text()` with no encoding, so it follows the locale. `cmd_update` does that before `coordinated` looks at the receipt. The receipt itself is ASCII (`json.dumps` escapes non-ASCII), which is why this is not a read of the receipt file.

Reproduction: `Review6.test_f02_locale_retry_keeps_the_accepted_description`. A claiming update of a UTF-8 file `café body\n` is accepted and the acknowledgement is lost.

- `LC_ALL=en_US.ISO8859-1` (and `PYTHONUTF8=0`) retries with exit 0 and stores `cafÃ© body\n`. One extra `set`.
- `LC_ALL=C` raises `UnicodeDecodeError` before the receipt is consulted. The receipt survives, a peer that syncs still has `café body`, and a later UTF-8 retry is one `set`. The C retry itself is a traceback and exit 1.

```diff
--- a/bead
+++ b/bead
@@ def text_arg
-        return sys.stdin.read() if path == "-" else Path(path).read_text()
+        raw = sys.stdin.buffer.read() if path == "-" else Path(path).read_bytes()
+        try:
+            return raw.decode("utf-8")
+        except UnicodeError as error:
+            raise BpError("VALIDATION", f"{name} is not valid UTF-8") from error
```

The same decode belongs on comment `--file` and on `import_records`' `read_text()`. With it, both locales compute the original signature and `settle_commands` returns done.

### F03 — High: some credential URLs are still stored, including in the file you commit

`without_password` only matches a lowercase scheme and a password that contains neither `@` nor `/`. These are stored in `meta.json`, returned by `info`, and written into `.beadroll.json` by `init --tracked` (mode 0600, which does not stop the owner from committing them):

| URL | Stored |
|---|---|
| `HTTPS://alice:supersecret@example.invalid/private.git` | unchanged, password included |
| `https://alice:sec/ret@example.invalid/private.git` | unchanged, `sec/ret` included |
| `https://supersecret@example.invalid/private.git` | unchanged; the token is the username |

Checked and already safe, in `test_remote_url_shapes_that_are_already_safe`: percent-encoded passwords (`s%65cret`, `sec%2Fret`, `p%40ss`) are stripped; `ssh://alice:supersecret@host` becomes `ssh://alice@host`; `ssh://alice@host` and `git@host:org/repo.git` are kept; a named remote `origin` whose URL is `https://alice:supersecret@…` is shown as `https://alice@…`.

```diff
--- a/bead
+++ b/bead
@@ def without_password
-    match = re.match(r"^([a-z][a-z0-9+.-]*://)([^/@]*):([^/@]*)@(.*)$", url, re.S)
-    if match:
-        return f"{match.group(1)}{match.group(2)}@{match.group(4)}", True
-    return url, False
+    match = re.match(r"(?i)^([a-z][a-z0-9+.-]*://)(.*)$", url, re.S)
+    if not match or "@" not in match.group(2):
+        return url, False
+    scheme, rest = match.group(1), match.group(2)
+    authority, _, tail = rest.rpartition("@")
+    if ":" in authority:  # password, including one that contains '/'
+        user = authority.split(":", 1)[0]
+        return (f"{scheme}{user}@{tail}" if user else f"{scheme}{tail}"), True
+    # https://TOKEN@host is how a personal access token is usually written.
+    # ssh://user@host has no password separator and must keep the user.
+    if scheme.lower() in ("http://", "https://"):
+        return f"{scheme}{tail}", True
+    return url, False
```

### F04 — Medium: `export -o` and `.beadroll.json` are mode 0600

`main` sets umask 077 for the whole process. That correctly makes `meta.json` 0600 (the passing test checks this). It also makes the tracked config, which the tool tells you to commit, and `export -o` into a checkout, mode 0600. On a shared working tree other users cannot read them. Git does not store that mode, so a later clone follows the cloner’s umask; the damage is the working tree bead just wrote.

Reproduction: `Review6.test_f04_checkout_files_stay_readable_in_a_shared_tree`. Both files are `0o600`.

Stop setting the process umask. Create store files and directories with an explicit `0o600` / `0o700`, and let `export -o` and `.beadroll.json` use the ambient umask (`write_atomic(..., private=False)` opening with mode `0o666`).

### F05 — Medium: TAB and U+2028 still reach the terminal

`CONTROLS` is `[\x00-\x08\x0a-\x1f…]`. That skips TAB (`\x09`). U+2028 and U+2029 are not in the bidi range. U+202E is escaped. Reproduction: `Review6.test_f05_human_output_escapes_tab_and_line_separators`. `create` of `col<TAB>FORGED<U+2028>line<U+202E>title` prints the tab and U+2028 raw and shows `\u202e`.

```diff
--- a/bead
+++ b/bead
-CONTROLS = re.compile("[\x00-\x08\x0a-\x1f\x7f-\x9f\u200e\u200f\u202a-\u202e\u2066-\u2069]")
+CONTROLS = re.compile("[\x00-\x1f\x7f-\x9f\u2028\u2029\u200e\u200f\u202a-\u202e\u2066-\u2069]")
```

JSON still contains raw U+202E and round-trips it (`test_json_keeps_bidi_text`). That is the §2 rule that JSON is untouched, not a second finding.

### F06 — Medium: a failed command with a closed stderr exits 120

The E07 handler dup2s only stdout to `/dev/null` and returns 0. A success whose stdout breaks still exits 0 with no traceback (`test_closed_stdout_on_success_exits_zero_and_store_stays_private`). A failure whose stderr breaks does not: `bead create` with the stderr pipe closed exits 120. The error text never lands, and the status is not the command’s 1.

Reproduction: `Review6.test_f06_failed_command_with_closed_stderr_keeps_its_status`.

Catch `BrokenPipeError` around the error print and return 1 or 2 from that path. On the success path, dup2 both stdout and stderr to `/dev/null` before returning 0, so process shutdown does not turn a caught pipe error into 120.

### F07 — Medium: non-UTF-8 input is a traceback, and `--json` gets no envelope

A title containing a surrogate (`\udcff`, what a non-UTF-8 argv byte becomes) passes `cmd_create` and then `encode_events` raises `UnicodeEncodeError` inside `writing`'s exit. `encode()` runs before `write()`, so the issue is not stored, but the process exits 1 with a traceback. A description file of bytes `caf\xff` does the same from `Path.read_text()`. Reproduction: `Review6.test_f07_non_utf8_input_is_a_structured_error`.

The file half is the UTF-8 decode in the F02 diff. For argv and other strings, reject a surrogate before emit:

```python
try:
    value.encode("utf-8")
except UnicodeEncodeError as error:
    raise BpError("VALIDATION", "text is not valid UTF-8") from error
```

### F08 — High: a dependency is not part of the import probe

`import_records` probes the create, then emits it, then emits `dep_add` for targets in the same file with no probe. `{"depends_on_id": "ex-b", "type": 1}` next to a valid `ex-b` imports with exit 0 and `{"imported": 2}`. `show ex-a` has no dependencies. `info` has one integrity row, `dep_add event has no valid target`. A dependency that is a string (`"dependencies": ["ex-b"]`) raises `TypeError` after the creates have been emitted in memory; the exit of `writing()` skips the append, so `ex-c` is not stored, but the caller gets a traceback rather than `VALIDATION`.

Reproduction: `Review6.test_f08_import_probes_dependencies_before_writing`.

Validate every dependency (object, string `depends_on_id`, type string or null) in the same pass as the create probe, before any `emit`. One failure raises `VALIDATION` and writes nothing.

### F09 — High: a dangling dependency removed before its target exists comes back, and can cycle

Three reproductions, all in `Review6.test_f09_dangling_dependency_can_be_retracted_before_its_target_exists`:

- Import A blocking missing `ex-b`. `dep remove ex-a ex-b` is `ISSUE_NOT_FOUND`. Import B blocking A. A now blocks B as well. Both are unready. `dep cycles` reports one cycle. A one-shot import of A-without-the-dep plus B has only B→A, so A is ready.
- Re-import A with the dependency deleted (the record is already known, so the import writes nothing), then import B. Same cycle.
- Hand-written journal, one chain: create A with dangling `ex-b`, then `dep_remove` whose `to` is B’s id, then create B depending on that removal. Replay adds the edge and A is blocked. `materialise_dangling` tags the edge with A’s create id and never looks at a removal that already ran.

A mutual pair imported in one file and in two batches has the same edges and the same empty ready set (`test_incremental_mutual_import_matches_one_shot`). The cycle start node can differ. That match is not this bug. The bug is a removal that does not survive until the target appears.

`dep remove` of an unknown key should emit `dep_remove` with `{"key": "ex-b"}` instead of `ISSUE_NOT_FOUND`. Applying that drops a dangling entry the writer had seen. `materialise_dangling` must not add an edge whose target uid is named by a `dep_remove` already applied on that issue. Re-import of a known id should emit those key removals for dangling targets the new record no longer lists, before the later create materialises them.

### F10 — High: `read_attempt` applies a claim when a later line is JSON but not an event

`read_attempt` returns `[]` only when `loads_strict` raises. `null` is valid JSON. A claim line plus `null` is loaded as two values; `journal.add` drops `null` as unidentified and applies the claim. The bundled title edit, which was the following line, is gone. Reproduction: `Review6.test_f10_non_event_json_makes_the_whole_attempt_inert`. After replacing an accepted claim-and-edit file with its first line plus `null`, `show` has a confirmed claim and the original title `attempt`.

```diff
--- a/bead
+++ b/bead
@@ read_attempt, inside the line loop
-            events.append(loads_strict(line))
+            event = loads_strict(line)
+            problem = None if isinstance(event, dict) else "attempt line is not an event"
+            if problem is None:
+                problem = event_problem(event) or payload_problem(event)
+            if problem:

+                    problems.append({"event": None, "origin": f"{path}:{number + 1}",
```

`payload_problem` runs only after `event_problem` has accepted the envelope. Any failure voids the file.

### F11 — High: a leftover pending twin that is not byte-identical is reported as a second machine

`Link.merge` raises `ATTEMPT_FORK` whenever `pending/<id>.json` differs from the remote blob, before it notices that the local claims file already matches that blob. Reproduction: `Review6.test_f11_stale_pending_twin_does_not_fork_a_matching_attempt`. Sync the claim, then write the accepted bytes plus one newline into `pending/<id>.json`. `sync` exits 1 with `ATTEMPT_FORK` and the copied-identity message. The claim on disk is the remote’s.

If `target.read_bytes() == theirs`, unlink the pending twin and its `.command` and continue. If there is no local claims file, or it differs too, keep `ATTEMPT_FORK`.

### F12 — Medium: one unreadable pending file fences a new commit on every sync

`pending_files` is every `pending/*.json`. `load_pending` drops what `read_attempt` cannot parse, and `drop_pending` only unlinks what `load_pending` returned. `synchronise` still sets `fence=bool(pending_files(...))`. Reproduction: `Review6.test_f12_unreadable_pending_file_is_not_fenced_forever`, and a probe that counted commits: two syncs took `refs/beads/journal` from 2 commits to 4, and the `{` file was still there.

Before fencing, unlink a pending file that `read_attempt` does not return as events (and its `.command`). Do not fence it.

### F13 — Medium: `meta.json`, `replica.json` and `aliases.json` are not strict

They use `json.loads`. `loads_strict` is not applied, and a wrong shape is not a `BpError`.

- `meta.json` `{"last_sync": NaN}` makes `info --json` exit 0 with `NaN` in the document. `loads_strict` rejects it.
- `replica.json` `{"id": NaN}` does the same (`"machine": NaN`). The next `create` then dies with `KeyError` on the event id: the id’s replica is not a string, replay ignores the event, and `cmd_create` indexes it anyway.
- `aliases.json` `[1, 2]` makes `machines` raise `TypeError` (`dict.update` of a non-pair). That is not an `OSError` or `ValueError`, so the `suppress` does not catch it.

Reproduction: `Review6.test_f13_local_state_files_are_strict_json`.

Read all three with `loads_strict`. Require `meta` and `aliases` to be objects (ignore or `CONFIG`/`IDENTITY` otherwise; aliases values must be strings). Require `replica.json`'s `id` to be an 8-hex string or raise `IDENTITY` before any command uses it.

### F14 — Medium: a clock past year 2100 turns `create` into `KeyError`

`uuid7` puts `time.time_ns()` in the id. `event_problem` rejects a millisecond stamp after `MAX_MILLIS` (year 2100). `Tx.emit` does not check that. `cmd_create` then does `tx.state.issues[uid]` on an event replay will not apply. Reproduction: `Review6.test_f14_future_clock_create_is_a_structured_error`, with `time.time_ns` fixed at `4_429_000_000_000_000_000`. Exit 1, traceback, `KeyError`, and the title is not stored.

Raise `BpError("VALIDATION", …)` from `Tx.emit` when `event_problem` or `payload_problem` is set, before the event is added and before the command indexes it.

A clock 48 hours behind does not break causality: after B has synced A’s title, B’s update still replaces it and there is no conflict (`test_clock_skew_does_not_override_causality`). Two unseen updates, one of them 48 hours behind, both remain as a conflict. That is the §2 rule that the displayed value is the newest event id.

### F15 — Medium: a timed-out fetch leaves `git-upload-pack` running

`run_git` uses `subprocess.run(..., timeout=)` and does not start a new session. Git runs `git-upload-pack` from `GIT_EXEC_PATH` as a grandchild. The timeout kills git. The helper stays.

Reproduction: `Review6.test_f15_timeout_reaps_the_git_helper`. A local bare remote, `GIT_EXEC_PATH` whose `git-upload-pack` sleeps 30s, `BEAD_NET_TIMEOUT=2`. `sync` returns `REMOTE_UNREACHABLE` and no traceback. The helper pid is still alive (the test then kills it). A normal `sync` afterwards succeeds.

```python
proc = subprocess.Popen(["git", *args], start_new_session=True, ...)
try:
    stdout, stderr = proc.communicate(input=data, timeout=timeout)
except subprocess.TimeoutExpired:
    os.killpg(proc.pid, signal.SIGKILL)
    proc.communicate()
    raise BpError("REMOTE_UNREACHABLE", ...) from None
```

### F16 — Medium: a read-only store, and a full volume, fail as tracebacks

`test_reads_work_when_the_store_is_read_only` only requires a non-zero status. The write is a `PermissionError` on `open(store/lock)`. Reproduction: `Review6.test_f16_read_only_store_write_is_a_structured_error`. `show` of the earlier issue still works once you catch the traceback; the test’s read of it is after the failed create, and the existing title is intact when the directory is writable again. I also chmod’d the store to `a-w` while `sync` was blocked in a sleeping `git-upload-pack`. That command returned `REMOTE_UNREACHABLE` (the timeout, not a permission error). After `u+w`, `create` succeeded and both the old issue and the new one were listed.

A 16 MiB HFS+ image, filled until a one-byte write returned `ENOSPC` (`df` showed 0 available, 100%):

- A 200KB `create` exited 1 with `OSError: [Errno 28] No space left on device` from `segment.write`, traceback, and the issue was not in the following `list`.
- Deleting the filler and creating again exited 0. `list` contained only that later issue.

So a full volume does not poison the next write. It does not produce a structured error either. The same `OSError` handler around `locked` / `writing` / `append_events` should raise `BpError("IO", …)` for both `EACCES` and `ENOSPC`. A small append can still succeed when `df` says the volume is full, if it fits in the segment’s already allocated last block; the 200KB create is the one that actually required a new block.

## Observations

These are not findings. They are what the new code did when the author’s tests were the right shape, plus one line that is not a feature request.

- `prime` said `2 ready` on a store with an open issue, a blocked issue, an offline claim, a deferred issue, a closed issue, an epic and its open child. `bead ready` returned those same two ids.
- `help`, `help claim`, `prime`, `onboard` and `--help` in a directory that is not a git repository, with a fresh `BEAD_HOME`, exited 0 and created no files.
- Another actor’s failed claim does not delete your receipt. `sync` does not either. A changed `--description-file` or a changed stdin is a new request and is applied. Adding `--json` on the retry of the same update is still one `set`.
- The in-process `receipt` tuple returns the result of this call’s own uncertain push once merge sees that attempt. I did not find a second command or a second actor inside that loop that it treats as the same work.
- JSON output keeps U+202E in the title and parses back to the same string. Human output escapes it.
- Store `meta.json` is mode 0600. `.beadroll.json` being 0600 is F04, not this.
- A persisted projection is still the limit the README already states; nothing in this review changes that.

## What has to be true before other people run this

In this order:

1. A retry of a command the remote already accepted is that command. A failed command in between must not drop the receipt, and the retry must not depend on the locale staying UTF-8. Until then an agent that crashes, mistypes the next id, and retries will be told the close failed, or will overwrite the description.
2. A credential in a remote URL does not land in `meta.json`, `info`, or `.beadroll.json`. Uppercase schemes, a slash in the password, and an https token in the username still do, and `--tracked` writes them into a file the tool tells you to commit.
3. Import of a record is all of it or none of it, dependencies included. Today a bad `type` imports the issues, drops the edge, and exits 0.
4. An attempt file is one transaction. A later `null` must not confirm the claim. A pending file that is junk, or that differs only from a copy you already have, must not stop sync or add a fence commit forever.
5. A dependency taken back before its target exists stays taken back when the target arrives, including a re-import that no longer lists it. Otherwise a later batch closes a cycle the corrected file does not have.
6. Human output does not emit a raw tab or a Unicode line break. A failed command stays failed when stderr breaks, with its own status. Non-UTF-8 input is `VALIDATION`, not a traceback.
7. Files bead writes into the checkout follow the caller’s umask. The store stays 0600/0700 by its own file modes, not by a process-wide umask.
8. A damaged `replica.json` / `meta.json` / `aliases.json`, a clock past 2100, a full volume, and a read-only store all fail as `BpError`s. A timed-out fetch does not leave `git-upload-pack` running.

The shipped stress suite, the 3.12 fast suite, causality under a skewed clock, `prime` against `ready`, and help outside a repository do not need to move before those.
