## Assessment

The healthy-journal baseline remains green, and the independent exhaustive check of every
directed graph through four nodes supports the repaired cycle enumerator. The review found
**11 new finding families**, however: four affect synchronized state, accepted-operation
recovery, or terminal ownership during normal or explicitly hostile workflows; one makes
incremental import produce wrong readiness; and six expose integrity/robustness boundaries.

The highest-impact result is that ownership-attempt files are called immutable but are not
compared. A damaged foreign copy is silently pushed over the accepted remote transaction,
and a fresh peer then observes a confirmed claim without its bundled edits. Separately, retrying
an accepted claiming parent move after the documented crash hook removes the newly accepted
parent on every peer. An older client also accepts a future manifest, rewrites the authoritative
tip as format 1, and drops future-only files from that tip. These are implementation failures,
not objections to
persistent claims, thread ownership, single-ref serialization, or any decision in
`REVIEWING.md` section 2.

## Findings, ranked by impact

### Q01 — High: a damaged immutable attempt can replace the accepted remote transaction

`Link.merge` records the existence of an ownership path and immediately continues whenever the
local target exists (`bp:1514-1519`). It never compares the local blob with the remote blob.
`Link.tree` then rebuilds the next commit from local files (`bp:1562-1583`). `unpublished()`
also reports zero because it compares paths, not content.

Reproduction:
`ProtocolReview4.test_q01_damaged_immutable_attempt_cannot_replace_remote_transaction`.
A published `update --claim --title accepted --add-label kept` is one three-line attempt. After
B syncs it, the test truncates only B's foreign copy to the claim line and runs `bp sync`.
The command exits zero and reports `pushed: 0`, but the remote blob becomes one line. Fresh C
sees the confirmed claim with the old title and no label. A still has the complete file and can
push it back later, so peers can oscillate as well as lose the current projection.

The same transaction boundary fails before sync:
`test_q01_malformed_attempt_is_inert_as_a_whole` writes a valid claim line followed by `{`.
`read_attempt` reports the bad line but returns the valid prefix (`bp:358-375`), so the malformed
file confirms a claim. Expected: an immutable attempt is accepted in full or is wholly inert;
a local/remote mismatch is repaired from the authoritative copy or fails closed.

This is related to A02/N02 but is not their reproduction: segment fork propagation and
multi-file confirmation were fixed before ownership moved into one supposedly immutable JSONL
file. The new file type has no equality check and its parser is not transactional.

### Q02 — High: rebuilding an accepted state-dependent update deletes its own relationship

Reproduction:
`ProtocolReview4.test_q02_retry_after_accepted_claiming_parent_move_keeps_parent`.

1. Child C starts under P1; A and a peer are synchronized.
2. A runs `update C --claim --parent P2` with `BP_TEST_CRASH_AFTER_PUSH=1`. The remote accepts
   claim + remove(P1) + add(P2); A exits 99 before local confirmation.
3. A immediately retries the identical command.

The retry returns success, but C has no parent on A or the peer. Recovery confirms the first
attempt and then rebuilds the command. Because current state is already P2, `edits()` emits
remove(P2) (`bp:1994-1998`); event-level `already_done` suppresses the already accepted add(P2)
but not this newly derived inverse (`bp:1047-1059`). The log ends with remove(P2).

`test_q02_retry_after_accepted_claiming_close_emits_one_close` shows a second symptom: the same
crash/retry appends two closes because the accepted close contains `{"claim": id}` and the
rebuilt close contains `{}`. The later close replaces the accepted timestamp/provenance.

N01's exact release and identical-edit cases are fixed, but event-by-event deduplication cannot
make a state-dependent command idempotent. Recovery needs a durable command/attempt identity and
must return the accepted attempt's result as a unit instead of rerunning its builder.

### Q04 — High: a future manifest is silently downgraded and omitted from the new tip

Reproduction:
`ProtocolReview4.test_q04_future_manifest_is_refused_without_remote_rewrite`.
A disposable adversary clone publishes the same workspace with `manifest.format = 2` and a
`future-state.bin`. A fresh current client runs `sync`.

`Link.fetch` validates only `workspace` (`bp:1474-1483`). Sync exits zero, creates a descendant
whose manifest is format 1, and omits `future-state.bin`, even while reporting `pushed: 0`.
The crafted future commit and blob remain reachable as its parent, but no longer appear in the
authoritative tip/tree. Expected: reject every unsupported manifest format before importing or
publishing, leaving the remote tip and tree byte-for-byte unchanged. The first three reports
explicitly listed future manifest formats as not run.

### Q05 — High: release resurrects an issue tombstoned by `update`

Reproduction:
`CommandsAndCompatibilityReview4.test_q05_tombstone_update_cannot_leave_a_releasable_claim`.
`update X --claim --status tombstone` succeeds with a confirmed claim still attached. A routine
`release X` then succeeds and writes status `open`, resurrecting the tombstoned issue.

`cmd_update` special-cases only closed/open and emits tombstone as a generic register write
(`bp:1982-1987`). Release always writes open for a matching confirmed claim (`bp:912-923`).
Expected: reject `update --status tombstone` in favor of `delete`, or give it delete semantics
and end the claim. This is a normal CLI path, not a corrupt-input case.

### Q03 — Medium: a crash after local confirmation makes an accepted release retry fail

Reproduction:
`ProtocolReview4.test_q03_crash_after_confirmation_before_cleanup_is_idempotent` injects the
crash boundary between `confirm_ownership` and `drop_pending` (`bp:1716-1717`). Disk then holds
both the final accepted release and its pending twin. State is correctly open.

On retry, `Link.merge` sees that the final target exists and continues without recognizing or
removing the matching pending file (`bp:1518-1519`). A fence drops the pending twin, the release
builder is rerun, and the command returns `NOT_OWNER`. Expected: compare the two files, recognize
the accepted attempt, populate `confirmed_events`, remove pending, and return success. This is an
uncovered local-durability boundary adjacent to N01, not its earlier after-push/before-confirm
case.

### Q06 — Medium: split imports never activate a dependency when its target arrives

Reproduction:
`CommandsAndCompatibilityReview4.test_q06_incremental_import_resolves_late_dependency_target`.
Import A(blocks B) before B exists, then import B. Compare with importing the same two records in
one call.

The exports are identical, but the live projections are not. Split import shows no dependency,
reports A unblocked, and returns both A and B from `ready`; one-shot import shows A blocked and
only B ready. `import_records` saves the first edge under `_dangling_dependencies`, then examines
dependencies only on newly created records (`bp:1763-1789`), never revisiting A when B arrives.
The command accepts repeated imports and its contract says it keeps relationships; it documents
no whole-snapshot or one-shot-only restriction. On that interface, batching the same records
should not change live semantics. The result is wrong readiness under an ordinary incremental
use, hidden by an interchange export that still carries the dangling record. If repeated import
is intentionally unsupported, the command should reject it explicitly instead.

### Q07 — Medium under corrupt input: an invalid placeholder bridges a broken journal chain

Reproduction:
`ReplayReview4.test_q07_invalid_placeholder_cannot_bridge_a_broken_machine_chain`.
Machine A writes valid set S1, then an envelope-invalid event that depends on the create rather
than S1, then valid set S2 depending on the invalid ID.

Phase 1 exempts invalid/quarantined placeholders from the predecessor check but advances A's
version-vector position anyway (`bp:786-801`). Replay therefore says S2 saw S1, applies S2, and
reports no chain break. The explicit deps say it did not. Expected: the placeholder and its tail
cannot cross the broken chain or invent ancestry. This is the placeholder boundary of A04's
invariant, not the already-fixed valid split-segment reproduction.

### Q08 — Medium: `dep tree` crashes on a valid 1,100-node chain

Reproduction: `DeepTreeReview4.test_q08_deep_valid_dependency_tree_does_not_overflow` builds
1,100 valid issues and 1,099 causal block edges, then runs the real JSON CLI. Replay is clean,
but the recursive tree walker (`bp:2200-2212`) raises `RecursionError` and emits a traceback.
The iterative cycle scanner fixed R11/D01; earlier reports explicitly noted that `dep tree` had
only been inspected, not executed. Use an explicit `(node, depth)` stack while retaining the
current cycle/duplicate display behavior.

### Q09 — Medium under hand-written input: accepted required-register clears crash queries

Reproduction: `ReplayReview4.test_q09_required_register_clears_remain_queryable` separately
settles `None` for `title`, `priority`, and `issue_type`. All three events pass validation and
produce no integrity entry. `write_register` removes the materialized key, after which `brief`
and `line` index it directly and raise `KeyError` (`bp:728-745`, `bp:1318-1321`).

The public CLI does not generate these clears; this is a hand-written/corrupt-input robustness
case. The checklist explicitly asks for `None` against a value on every register, and replay
currently accepts the events as valid. Previous tests verified register contents but queried only
optional clears. Preserve query-safe defaults for required display fields, or reject such clears
during validation.

### Q10 — Medium: a preserved unknown import field can poison export bookkeeping

Reproduction: `CommandsAndCompatibilityReview4.test_q10_reserved_dangling_extra_cannot_crash_export`.
An otherwise valid Beads record contains unknown field `_dangling_dependencies` with a string
value. Import succeeds and replay reports no integrity problem. Export then uses that user value
as its private list and raises `TypeError` at `deps + dangling` (`bp:1415-1425`).

Unknown fields are promised round-trip preservation. Private projection bookkeeping therefore
needs a namespace or state slot that cannot collide with imported `extra`, plus type validation
before any internal value is consumed.

### Q11 — Low: offline close leaves a provisional claim on the closed issue

Reproduction: `CommandsAndCompatibilityReview4.test_q11_offline_close_ends_a_provisional_claim`.
B makes an offline claim from the common frontier. A independently makes an offline claim and
closes it, then both sync. The closed issue retains both provisional claims in `show`/`claims`;
only B's truly concurrent claim should remain. `apply_event` clears provisional claims only inside
the branch that found a confirmed claim (`bp:927-940`). Provisional claims are deliberately
non-exclusive, so this does not create two confirmed owners, but it presents stale ownership after
a terminal transition. Expected: a close removes every provisional claim in its causal past while
preserving a concurrent provisional claim for conflict visibility.

## Design observations and accepted decisions

- A one-file ownership attempt is a sound atomic-publication shape only if the whole file is parsed
  transactionally and every same-path copy is content-address checked. Atomic rename alone does not
  establish immutability after installation.
- Export equality is not a sufficient import oracle: Q06's split and one-shot stores export the same
  dependency record while answering `ready` differently.
- The exhaustive small-graph result gives positive evidence for the present Johnson implementation;
  it does not question the accepted 200-cycle cap.
- No finding objects to non-expiring claims, thread ownership, `in_progress` as claim, newest-ID
  conflict display, local owner close, child renumbering, quarantine of one duplicate ID, lock-held
  pushes, single-ref contention, bitset memory tradeoffs, hash-range comment IDs, lack of a persisted
  projection, or local-only trackers. Q01-Q11 are failures around those decisions, not requests to
  reverse them.
